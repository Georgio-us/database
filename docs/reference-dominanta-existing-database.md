# Референс действующей базы недвижимости Доминанта

Статус документа: дословная фиксация подробного конспекта Zoom с администратором действующей базы.

Назначение документа: сохранить устройство, рабочие сценарии, сильные стороны, ограничения и накопленную бизнес-логику реально используемой системы для последующего анализа при проектировании новой базы.

Правила использования:

- документ является референсом существующей системы, а не техническим заданием;
- перечисленные функции не считаются автоматически согласованными требованиями нового продукта;
- решения из этого документа переносятся в продуктовую документацию только после отдельного обсуждения и подтверждения;
- устаревший интерфейс и техническая реализация не рассматриваются как образец для копирования;
- исходное содержание Zoom-конспекта ниже сохранено полностью, в исходной последовательности и без смысловых сокращений.

Источник: текст, переданный пользователем после Zoom-разбора базы агентства недвижимости «Доминанта».

## Полный конспект

1. Общий контекст

В рамках Zoom была подробно разобрана действующая внутренняя база недвижимости агентства «Доминанта», работающая в связке с Bitrix

Основная задача разговора - понять:

* как устроена база объектов
* как в ней работают риелторы
* какие существуют сущности и роли
* как работают подборки и заявки клиентов
* как происходит актуализация объектов
* как устроены фильтры
* как объекты выгружаются на сайт
* как формируются презентации
* как работает история изменений
* какие функции реально используются
* какие функции устарели или фактически не используются
* какие проблемы есть в текущей системе
* какие решения желательно перенести или улучшить в новой базе

Ключевой общий вывод - несмотря на возраст системы и множество неудобств, в ней накоплена довольно сильная прикладная логика именно для работы агентства недвижимости

При создании новой системы имеет смысл не копировать интерфейс или техническую реализацию один в один, а сохранить полезную бизнес-логику и убрать исторически накопившиеся ограничения

2. Основная сущность - объект недвижимости

Основная рабочая сущность - карточка объекта

Для квартир карточка содержит большой объём информации, включая:

* фотографии
* заголовок
* описание
* внутренний комментарий
* цену
* площадь
* количество комнат
* этаж
* этажность дома
* технические характеристики квартиры
* характеристики дома
* район
* микрорайон
* улицу
* ЖК
* ответственного риелтора
* владельца объекта / собственника
* номер телефона собственника
* условия сотрудничества
* эксклюзивность
* комиссию
* возможность торга
* дополнительные параметры
* документы
* планировку
* видео
* историю работы с объектом
* статус объекта
* статус обзвона
* выгрузки
* связанные заявки
* аналоги

Карточка фактически выступает центральным экраном объекта

При открытии объекта пользователь сразу видит:

* фотографии
* основную информацию
* цену
* характеристики
* данные по дому
* контакты
* ответственного
* доступные действия

Это важная особенность системы

Пользователь подчёркивал, что именно такой формат гораздо удобнее, чем системы, где фотография, характеристики, документы и прочее разнесены по отдельным вкладкам

3. Визуальный формат списка объектов

Одна из сильных сторон базы - визуальный список объектов

Объекты отображаются примерно по принципу маркетплейса или OLX:

* фотография
* адрес / ЖК
* краткие параметры
* цена
* площадь
* дата добавления
* дата обновления
* ответственный
* ID
* дополнительные статусы

Это позволяет риелтору уже по главной фотографии быстро визуально определить:

* квартира после строителей
* обычный ремонт
* современный ремонт
* дорогой ремонт
* цветовая гамма
* примерное состояние

Например, если клиент просит квартиру в серых тонах, риелтор может визуально отбрасывать неподходящие варианты, не заходя в карточку каждого объекта

Это сильно ускоряет работу по сравнению с системами, где список представляет собой таблицу, а фотографии приходится открывать внутри каждой карточки отдельно

4. Разные варианты отображения объектов

В системе есть несколько видов отображения списка:

1. карточки с фотографиями
2. более компактный список без фотографии
3. ещё один визуальный режим, похожий на презентационный / плиточный

По мнению пользователя, большого смысла делать множество режимов отображения в новой системе нет

Главное - сделать один удобный визуальный режим с фотографией и ключевой информацией

Дополнительный компактный режим может быть полезен, но не является критически важным

5. ID объекта

Каждому объекту автоматически присваивается уникальный ID

ID активно используется в повседневной работе

Например, на внутреннем собрании могут обсуждать 20 квартир и называть только их ID

После этого риелтор может вставить несколько ID через запятую и получить подборку конкретных объектов

Поиск по ID имеет приоритет над другими фильтрами

Если введён ID, остальные выставленные фильтры не мешают отображению нужного объекта

Это полезное поведение, которое стоит сохранить

6. Ответственный риелтор

У каждого объекта есть ответственный риелтор

В карточке отображаются:

* имя ответственного
* контакт
* принадлежность к филиалу

Ответственный имеет расширенные права на свой объект

Он может изменять:

* технические параметры
* площадь
* этаж
* количество комнат
* описание
* фотографии
* документы
* внутреннюю информацию
* другие поля карточки

7. Открытая база объектов

В «Доминанте» используется принцип открытой базы

Все риелторы видят все объекты агентства

Обычный риелтор может открыть чужой объект и увидеть:

* фотографии
* параметры
* цену
* информацию
* собственника
* номер телефона собственника

Это отличается, например, от модели «Атланты», где база более закрытая

В «Атланте»:

* другие риелторы видят объект
* не видят полный адрес
* не видят телефон собственника
* по объекту взаимодействуют через ответственного риелтора

В «Доминанте» обычный объект открыт внутри компании

8. Права редактирования чужого объекта

Несмотря на открытую базу, полный доступ к редактированию есть только у ответственного

Чужой риелтор не может изменить:

* этаж
* площадь
* количество комнат
* другие основные технические характеристики

Но любой риелтор может менять ограниченный набор оперативной информации

В частности:

* цену
* внутренний комментарий
* статус обзвона

Логика заключается в том, что другой риелтор может непосредственно связаться с собственником и получить новую информацию

9. Актуализация чужого объекта

Очень важная рабочая логика

Пример:

Риелтор подбирает квартиру клиенту

Находит объект другого риелтора

Вместо того чтобы звонить ответственному, он может позвонить непосредственно собственнику

Уточняет:

* квартира ещё продаётся или нет
* изменилась ли цена
* можно ли предлагать её клиенту

Если собственник говорит:

* квартира актуальна
* цена изменилась с 60 000 до 58 000

риелтор может внести соответствующие изменения в допустимые поля

Если собственник сообщает, что объект уже продан, риелтор может изменить статус обзвона на «Продано»

10. Уведомления ответственному

Если другой пользователь изменяет информацию по объекту, ответственному приходит уведомление через Bitrix

Например:

«Татьяна Кузнецовская изменила статус обзвона объекта N с актуального на продано»

Это позволяет ответственному быстро увидеть, что с его объектом произошло какое-то изменение

Подобный механизм уведомлений стоит предусмотреть в новой системе

11. Статус объекта

У объекта существует отдельный статус объекта

Среди упомянутых статусов:

* в продаже
* актуальное предложение
* задаток
* отложен
* снят в архив
* продан в архив

При статусе «Отложен» необходимо указать дату, до которой объект отложен

После этого в карточке видно, что объект отложен и до какой даты

12. Первичная модерация объекта

Когда риелтор первоначально добавляет квартиру, она получает статус «В продаже»

Далее офис-менеджер проверяет правильность заполнения карточки

После проверки офис-менеджер переводит объект в статус «Актуальное предложение»

Только после этого объект может попасть на сайт

Таким образом:

1. риелтор создаёт объект
2. объект получает первоначальный статус
3. офис-менеджер проверяет заполнение
4. выставляет «Актуальное предложение»
5. объект допускается к публикации

13. Статус обзвона

Кроме статуса объекта существует отдельный статус обзвона

Это важная операционная сущность

Она используется для актуализации информации

Статус обзвона может поменять любой риелтор, даже если объект принадлежит другому человеку

Например:

* актуален
* продано
* возможно другие рабочие состояния

Это позволяет отделить юридический / системный статус объекта от результатов последней коммуникации с собственником

14. Актуализация базы

Автоматической обязательной актуализации объектов сейчас нет

Дата обновления меняется при любом изменении карточки

Например:

* поменяли цену
* добавили комментарий
* отредактировали информацию
* добавили фотографии

Дата обновления объекта становится новой

Но это не означает, что собственнику обязательно звонили

15. Массовый обзвон

В компании периодически проводится массовая актуализация объектов

На момент разговора было сказано, что подобный обзвон происходит примерно раз в квартал

Например, перед октябрьским обзвоном требуется, чтобы дата актуализации была не старше сентября

При этом пользователь вспоминал другую модель работы, где определённый день недели, например вторник, являлся «днём актуализации базы»

Текущий процесс в «Доминанте» ограничен масштабом

В базе около 55 000 объектов

У отдельных риелторов может быть по 800 объектов

Полностью прозванивать такие объёмы вручную невозможно

Потенциально новая система может содержать более умную механику актуализации:

* напоминания
* план обзвона
* приоритетные объекты
* просроченную актуализацию
* массовые задачи

16. История объекта

В карточке существует подробная история

Система фиксирует практически все действия

Например:

* кто открыл объект
* кто посмотрел объект
* кто изменил поле
* кто поменял статус
* кто отправил презентацию
* когда произошло действие

Пример из разговора:

открытие карточки фиксировалось несколько раз с конкретным временем, например 20:37 и 20:45

Таким образом история является полноценным activity log

Это важная функция для новой системы

17. История просмотров

Даже простой вход в карточку объекта записывается в историю

То есть система фактически знает:

* кто
* когда
* какой объект открыл

Это полезно для аудита и понимания работы пользователей

При проектировании новой системы стоит решить, насколько детально хранить такие события, поскольку слишком подробный лог может генерировать большое количество данных

18. Документы

К объекту можно прикреплять документы

Поддерживаются стандартные форматы:

* JPEG
* PDF
* изображения
* другие распространённые файлы

Документы загружаются вручную

Автоматического получения документов нет

19. Планировка

Планировка может загружаться отдельно от обычных фотографий

Таким образом план объекта является отдельным типом медиа

20. Фотографии

К объекту можно добавить много фотографий

Фотографии можно:

* загружать
* менять местами
* определять порядок
* выбирать, какие фотографии попадут на сайт
* выбирать, какие фотографии попадут в презентацию

Порядок фотографий в базе соответствует порядку фотографий на сайте

21. Отдельные настройки публикации фото

Для каждой фотографии можно независимо указать:

* показывать на сайте или нет
* включать в клиентскую презентацию или нет

Например, риелтор может добавить внутреннюю фотографию, которую нужно сохранить в базе, но не показывать клиенту

Это полезная логика и её желательно сохранить

22. Видео

В карточку можно добавить видео

Текущая схема:

1. видео размещается на YouTube
2. ссылка вставляется в карточку объекта
3. видео подтягивается в карточку

Функцией почти никто не пользуется, хотя технически она есть

В новой системе логичнее предусмотреть:

* YouTube / Vimeo ссылку
* возможно прямую загрузку видео
* превью видео

23. Юридическая информация

В карточке предусмотрены поля, связанные с документами и юридическим состоянием объекта

Например:

* на основании какого документа оформлено право собственности
* есть ли несовершеннолетние
* существуют ли другие юридические нюансы
* вопросы, связанные с военнообязанными
* возможные ограничения

Часть этих полей пользователи почти не заполняют

Тем не менее сама категория данных полезна

24. Объекты с арестом и проблемными документами

По текущим правилам квартиры, находящиеся под арестом, как правило, вообще не добавляются

Причина - объект фактически непродаваем

При проектировании системы стоит учитывать, что бизнес-правило агентства может запрещать определённые объекты ещё на этапе добавления

25. Цена объекта

В карточке хранится стандартная цена продажи

Дополнительно введена отдельная цена для продажи через государственные программы

Причина:

при продаже через некоторые государственные программы расходы продавца могут быть выше

Например:

* обычная цена - 60 000
* цена по госпрограмме - 62 000

Либо цена может оставаться одинаковой

26. Аренда

Исторически система поддерживала аренду

Поэтому в карточках сохранились поля:

* цена аренды
* дата освобождения объекта
* условия аренды

Сейчас агентство в основном занимается продажей

Некоторые бывшие поля аренды были переиспользованы

Например, поле цены аренды было заменено на цену по госпрограммам

Если квартира продаётся вместе с действующим арендатором, подобная информация сейчас обычно просто пишется во внутреннем комментарии

27. Эксклюзивные объекты

В системе есть специальная отметка эксклюзивного объекта - «X»

Эксклюзив работает иначе, чем обычный объект

Для обычного объекта внутри компании:

* риелторы видят номер собственника
* могут контактировать с собственником напрямую

Для эксклюзивного объекта:

* номер собственника скрывается
* коммуникация идёт только через ответственного риелтора

28. Комиссия по эксклюзиву

Упоминалась внутренняя модель распределения комиссии

Если другой риелтор продаёт обычный объект, ответственный получает меньшую долю

В качестве примера звучало около 10%

Если объект эксклюзивный, ответственный получает большую долю - около 30%

Раньше существовали варианты 20% и 30%

Сейчас используется 30%

Также можно указать фиксированное вознаграждение, например $3 000

Эта сумма может быть заложена в стоимость объекта

29. Дополнительные коммерческие параметры

В карточке присутствуют параметры вроде:

* торг
* обмен
* комиссия
* фиксированное вознаграждение
* эксклюзив

Эти параметры отображаются отдельными заметными маркерами

30. Аналоги объекта

Внутри карточки существует функция поиска аналогов

Система подбирает похожие объекты автоматически по заданным параметрам

Пример параметров:

* район
* цена ±20%
* площадь ±10%
* количество комнат ±0

Это позволяет быстро получить набор конкурирующих / сопоставимых объектов

31. Проблема архивных аналогов

Во время просмотра возник вопрос, почему в аналогах отображался проданный объект из архива

Важно различать:

* статус самого объекта
* состояние объекта внутри клиентской заявки

В заявках проданные объекты автоматически не показываются

Если объект когда-то был добавлен в заявку, а позже продан, информация о реакции клиента может оставаться в истории

32. Заявки клиентов

Отдельная ключевая сущность - заявка клиента

Заявка содержит критерии поиска

Например:

* район
* улица
* диапазон цены
* площадь
* комнаты
* другие параметры

Система автоматически сопоставляет объекты с заявкой

33. Автоматическое поступление объектов в заявку

Это одна из наиболее полезных функций текущей системы

Пример:

в базе сегодня 10 000 объектов

Есть заявка клиента:

* определённый район
* определённые улицы
* конкретные параметры

Риелтор не должен каждый день заново выставлять фильтры и проверять весь рынок

Если завтра в базу добавляется новый объект, подходящий под параметры заявки, он автоматически появляется внутри этой заявки

34. Работа риелтора с объектами внутри заявки

Риелтор открывает заявку клиента и видит новые подходящие объекты

Далее для каждого объекта может отметить:

* подходит
* не подходит

Если объект признан неподходящим, он больше не должен постоянно предлагаться пользователю в рамках этой заявки

По сути заявка выступает живым сохранённым поиском плюс системой обработки результатов

35. Новые объекты внутри заявки

Новые поступления располагаются сверху

Таким образом риелтор может каждый день открыть заявки и посмотреть только новые объекты, не перебирая всю базу

Это особенно важно, если ежедневно добавляются десятки новых квартир

Например:

в сутки в базе может появиться 50 объектов

Вместо просмотра всех 50 риелтор видит только те, которые соответствуют параметрам его клиентов

36. Статистика реакции по заявкам

Возле объекта может отображаться статистика реакции клиентов

Например:

* зелёные - подходит
* чёрные / нейтральные
* красные - не подходит

То есть видно, как объект оценивался внутри разных заявок

В разговоре встречался пример вида:

0 / 0 / 2

где две заявки отметили объект как неподходящий

37. Подборка объектов вручную

Помимо заявок существует ручной механизм выбора объектов

У каждой квартиры есть checkbox

Риелтор может:

1. выбрать несколько квартир
2. сформировать из них подборку
3. создать клиентскую веб-презентацию
4. сформировать PDF

38. Сохранение выделенных объектов

Выбранные галочками объекты сохраняются даже после перехода между разделами или перезагрузки страницы

Например:

выбрано 4 объекта

Пользователь вышел из раздела

Вернулся

Выбор остаётся

Это может быть удобно, но текущая реализация имеет проблему

39. Проблема сброса выбранных объектов

В одном режиме отображения отсутствует удобная кнопка «Снять весь выбор»

Чтобы убрать все галочки, приходится:

* переключаться в другой режим
* нажимать отдельную кнопку
* делать несколько лишних действий

В новой системе нужна очевидная кнопка:

«Снять выделение»

или

«Очистить выбор»

40. Презентации

В системе существует три основных формата презентации:

1. PDF для брокера
2. PDF для клиента
3. веб-презентация

41. PDF для брокера

PDF для брокера предназначен для внутренней работы

Он содержит расширенную информацию

Если формируется из списка объектов, это фактически печатная версия отображаемой страницы

Если формируется из карточки конкретного объекта, может содержать более подробную внутреннюю информацию

Также может включать карту

Функция исторически была полезна, когда риелторы активно печатали объекты на бумаге

Сейчас ценность существенно снизилась

42. PDF для клиента

PDF для клиента позволяет скрывать определённые поля

Например:

* номер квартиры
* номер дома
* карту
* пустые поля
* внутреннюю информацию

Вместо номера собственника указывается контакт риелтора, который сформировал презентацию

43. Веб-презентация

Веб-презентация считается более современным и полезным вариантом

Пользователь выбирает объект или несколько объектов и формирует публичную ссылку

Клиент открывает её с телефона

Он может:

* посмотреть фотографии
* увидеть характеристики
* открыть подробности
* переключаться между объектами

При этом скрывается внутренняя информация:

* номер собственника
* точный адрес при необходимости
* внутренние поля

Контактным лицом выступает риелтор

44. Живое обновление веб-презентации

Одна из сильных функций

Веб-презентация не является статичным снимком

Если информация в объекте меняется, она автоматически меняется и по ранее отправленной ссылке

Например:

была цена 59 700

риелтор изменил её на 59 600

после обновления веб-презентации клиент видит 59 600

Старую ссылку отправлять заново не нужно

Это полезная функция, которую стоит обязательно сохранить

45. Презентации из нескольких объектов

Можно выбрать несколько объектов

После этого сформировать одну веб-презентацию

Внутри клиент видит список объектов

Может нажать «Подробнее» и открыть конкретную квартиру

Фотографии можно листать прямо с телефона

46. Вывод по PDF

PDF-презентации воспринимаются как устаревшая функция

В новой системе приоритет стоит отдавать:

* web-презентациям
* ссылкам
* мобильному просмотру

PDF можно оставить как дополнительный экспорт, но не делать центральной функцией

47. Выгрузка объектов

В карточке существует отдельный раздел «Выгрузки»

Объект можно вручную отправлять на разные площадки

Ранее тестировались или поддерживались:

* сайт
* приложение
* OLX
* DOM.RIA
* другие площадки

На момент разговора реально используется в основном сайт

48. Выгрузка на сайт

Выгрузка происходит вручную

Риелтор или уполномоченный сотрудник нажимает:

«Выгрузить»

После подтверждения объект публикуется

Если объект опубликован, в интерфейсе появляется соответствующий индикатор, например значок глобуса / счётчик

49. Какие объекты можно публиковать

На сайт выводятся только объекты со статусом «Актуальное предложение»

Это связывает модерацию карточки с публикацией

50. Сайт агентства

Сайт получает информацию об объектах непосредственно из базы

То есть база выступает источником данных

На сайте отображаются:

* фотографии
* цена
* улица
* район
* описание
* характеристики
* ответственный риелтор
* опыт работы риелтора
* количество объектов риелтора

Точный номер дома может не публиковаться

51. Риелтор на сайте

На публичной странице объекта выводится ответственный риелтор

Информация о нём также подтягивается из базы

То есть сайт наполняется не только объектами, но и данными пользователей системы

52. Новостройки и международная недвижимость

На сайте также существуют разделы:

* новостройки
* международная недвижимость

При этом не было понятно, заполняются ли они из той же базы и кто отвечает за эти данные

Предположительно новостройки ведёт отдельный отдел

53. Фильтры - общая структура

В системе существуют два разных блока фильтрации

Условно:

1. расширенный / административный фильтр
2. основной фильтр для подбора недвижимости

54. Верхний расширенный фильтр

Верхний фильтр содержит большое количество параметров

В нём есть:

* тип дома
* состояние квартиры
* жилой комплекс
* застройщик
* статус объекта
* статус обзвона
* ответственный
* подгруппа
* департамент / филиал
* клиент / собственник
* дата создания
* условия сотрудничества
* тип предложения
* балкон
* терраса
* наличие фотографии
* наличие дел
* наличие сделки
* другие параметры

Из всего этого обычные риелторы активно используют преимущественно:

* тип дома
* состояние
* жилой комплекс

Остальные параметры чаще нужны административному составу

55. Фильтр по застройщику

Поле застройщика существует, но фактически не работает

Идея при этом полезная

Например можно было бы выбрать:

«Будова»

и увидеть все ЖК данного девелопера

Сейчас такой возможности нет

56. Поиск по ответственному

Можно ввести фамилию риелтора

Система покажет объекты людей с такой фамилией

Если одинаковая фамилия у нескольких сотрудников, могут выводиться объекты всех

57. Филиалы / департаменты

Можно фильтровать объекты по филиалу

Например:

* первый филиал
* четвёртый филиал
* несколько филиалов одновременно

58. Поиск по собственнику

Есть фильтр по клиенту / номеру телефона собственника

Идея полезная для проверки дублей

Например:

риелтор хочет добавить новую квартиру

вводит телефон собственника

проверяет, нет ли уже его объекта в базе

Но сейчас функция работает плохо из-за большого количества дублирующихся контактов

59. Проблема дублей клиентов

В CRM имеется много повторяющихся контактов

Из-за этого поиск по номеру собственника недостаточно надёжен

В новой системе важна нормализация клиентов

Например:

* уникальность телефона
* предупреждение о дубле
* объединение контактов
* привязка нескольких объектов к одному собственнику

60. Фильтр по дате

Можно выбирать:

* вчера
* текущий месяц
* прошлый месяц
* текущий квартал
* диапазон дат

Это удобно для:

* руководства
* статистики
* анализа новых объектов

При этом сами новые квартиры и так обычно отображаются первыми

61. Второй фильтр - подбор недвижимости

Второй фильтр больше ориентирован непосредственно на работу риелтора с объектами

В нём есть:

* все квартиры
* мои квартиры
* эксклюзивы
* мои + эксклюзивы
* архив
* удалённые
* область / регион
* населённый пункт
* административный район
* микрорайон
* ориентир
* ЖК
* другие географические параметры

62. Архив

Архивные объекты сохраняются в системе

Они не удаляются автоматически

Удалить объект окончательно может только модератор базы

63. Удалённые объекты

Удалённые объекты доступны только пользователям с более высоким уровнем доступа

Обычный офис-менеджер их не видит

Модератор базы видит

64. География

Географическая структура базы включает:

* область / регион
* населённый пункт
* административный район
* микрорайон
* ориентир
* улицу

Эти значения используются для фильтрации и подбора

65. Микрорайоны

Микрорайон - особенно полезная сущность

Причина - административный район слишком большой

Например Приморский район может включать совершенно разные зоны

Если клиент хочет квартиру именно в историческом центре, одного административного района недостаточно

Поэтому микрорайоны позволяют точнее описывать зону поиска

66. Искусственные / пользовательские микрорайоны

Некоторые микрорайоны или группы создавались специально для удобства работы риелторов

Например:

* группы ЖК
* отдельные крупные жилые массивы
* несколько комплексов одной зоны

Такие группы могут не совпадать с официальным административным делением, но полезны для бизнеса

67. Проблема ЖК с секциями

Текущая структура ЖК создаёт серьёзную проблему

Пример:

ЖК «Альтаир»

11 секций

Нумерация квартир в каждой секции начинается с 1

Система не умеет нормально различать одинаковые номера квартир внутри одного ЖК

Поэтому приходится создавать отдельные сущности:

* Альтаир 1 секция 1
* Альтаир 1 секция 2
* …
* Альтаир 1 секция 11

Для риелтора это неудобно

Чтобы найти все квартиры комплекса, приходится выбирать каждую секцию отдельно

68. Компенсация проблемы ЖК через микрорайоны

Из-за вышеописанной проблемы были созданы более крупные группы

Например:

* Альтаир
* Sky City
* El Park
* Жемчужины Аркадии
* Жемчужины на Французском
* другие группы

Риелтор может выбрать группу вместо перечисления каждой секции

В новой системе правильнее построить нормальную иерархию:

Застройщик
→ ЖК
→ очередь / корпус
→ секция
→ квартира

69. Адресный справочник

Адреса и улицы базы формируются вручную

Если нужной улицы нет, риелтор обращается к модератору

70. Добавление новой улицы

Для добавления новой улицы модератор запрашивает подтверждающий документ

Например:

* техпаспорт
* выписку
* другой правоустанавливающий документ

Документ должен содержать официальный адрес

71. Зачем запрашиваются документы для адреса

Главная причина - избежать ошибок и дублей

Например, риелтор может:

* ошибиться в названии улицы
* использовать старое название
* перепутать населённый пункт
* ошибиться в районе

Модератор смотрит официальный документ и добавляет адрес в том виде, в котором он юридически указан

72. Пример с неверным населённым пунктом

Риелтор может попросить:

«Добавить улицу X в Сухом Лимане»

Но по документам объект может относиться к Ленпосёлку или другому населенному пункту

Если добавлять данные без проверки, база постепенно заполнится дублями и неправильными адресами

73. Переименование улиц

После официальных переименований улиц модератор вручную обновляет адресный справочник

Это дополнительная постоянная нагрузка

74. Альтернативная логика для новой системы

Обсуждалась более современная модель

Вместо того чтобы заранее вручную создавать весь справочник Одессы и области, можно:

* использовать данные карт
* использовать внешний адресный справочник
* позволять риелторам вводить новый адрес
* отправлять неизвестный адрес на модерацию

То есть риелтор создаёт новую улицу или объект, но запись получает статус «На проверке»

Модератор подтверждает или исправляет её

75. Google Maps / карты

Возникла идея использовать карты как основу справочника адресов

Например Google Maps

Но юридический адрес всё равно может отличаться от картографического

Поэтому оптимальная модель:

* карта помогает пользователю найти адрес
* официальный адрес хранится отдельно
* при необходимости проходит модерацию

76. Разработчики и обслуживание системы

Система исторически была разработана на базе Bitrix

Первоначальные разработчики, по словам собеседника, находились в России

После начала полномасштабной войны сотрудничество с ними прекратилось

Сейчас остались другие разработчики, которые могут поддерживать систему

77. Ограничения текущей разработки

Нынешние разработчики способны делать небольшие изменения

Например:

* переименовать поле
* изменить существующий параметр
* немного изменить логику

Но существенные изменения структуры базы либо невозможно сделать, либо они очень дорогие и трудоёмкие

78. Почасовая модель разработки

Разработчики работают по часам

Для задачи они оценивают количество часов

Например:

* 1 час
* 3 часа
* несколько дней
* неделя

Компания принимает решение, стоит ли платить за изменение

Из-за этого некоторые улучшения не реализуются, если руководство считает, что они нужны только ради удобства сотрудников

79. Модератор базы

Есть отдельный штатный сотрудник - модератор базы

Модератор:

* управляет адресным справочником
* добавляет улицы
* проверяет документы
* исправляет данные
* может видеть удалённые объекты
* имеет повышенные права
* общается с разработчиками
* инициирует технические изменения

Таким образом модератор является связующим звеном между пользователями и технической командой

80. Уровни доступа

В системе явно существует несколько уровней доступа

Минимально можно выделить:

Риелтор

* видит общую базу
* редактирует свои объекты
* может менять ограниченные поля чужих объектов
* работает с заявками
* делает подборки
* создаёт презентации

Офис-менеджер

* дополнительные административные функции
* может проверять объекты своего филиала
* может менять статус объекта
* вероятно может редактировать объекты своего филиала

Модератор базы

* работает со справочниками
* видит удалённые объекты
* управляет данными
* взаимодействует с разработчиками

Разработчик

* изменяет техническую структуру системы

В новой системе роли и права желательно описать явно через RBAC

81. Частные дома

Помимо квартир существует отдельная категория «Частные дома»

Основная логика карточки похожа на квартиру

Но есть дополнительные поля, связанные с:

* земельным участком
* домом
* материалом строительства
* перекрытиями
* этажностью

При этом заметно, что архитектура системы исторически была построена вокруг квартир, а потом частично адаптирована под другие типы недвижимости

82. Недостаточная адаптация под дома

Некоторые поля выглядят не совсем логично для дома

Например могут присутствовать параметры, больше характерные для квартир

Это показывает, что в новой системе стоит создавать отдельные схемы полей в зависимости от типа недвижимости

83. Земельные участки

Участки существуют как отдельная категория объектов

В карточке меньше информации

Основное:

* площадь
* адрес
* коммуникации
* описание
* фотографии
* юридическая информация

Участок может быть:

* пустой
* с домом
* с другими строениями

84. Дом и участок как отдельные юридические сущности

В реальности дом и земля могут оформляться отдельными документами

Поэтому возможна ситуация, когда дом и участок фактически продаются вместе, но юридически являются отдельными объектами / сделками

Также бывают дома без оформленной земли

Поэтому в новой системе желательно предусмотреть связь:

«Дом расположен на земельном участке»

при этом дом и участок могут оставаться отдельными сущностями

85. Неузаконенные строения

Встречаются объекты, где часть строений не узаконена

Например пристройка без документов

Покупатель приобретает такой объект с риском

Система потенциально должна позволять хранить юридические замечания такого типа

86. Коммерческая недвижимость

Для коммерческой недвижимости существуют дополнительные поля

Например:

* тип помещения
* общая площадь
* полезная площадь

Остальная логика похожа на другие объекты

87. Сортировка

Риелтор может сортировать результаты по различным параметрам

Например:

* количеству комнат
* этажу
* площади
* цене

По цене:

* от дешёвых к дорогим
* от дорогих к дешёвым

Сортировка сохраняется при смене вида списка

88. Реальный сценарий использования сортировки

Например риелтор выбирает:

* ЖК «Атмосфера»
* однокомнатные
* без ремонта

После этого сортирует квартиры по цене от меньшей к большей

Получает наиболее дешёвые варианты сверху

Это один из типичных рабочих сценариев

89. Проблема фильтров

Одна из заметных UX-проблем - фильтры из разных панелей одновременно влияют на результат

Пользователь может забыть, что где-то ранее был установлен фильтр

В результате система неожиданно показывает неполную выборку

90. Сброс фильтров

Нет очевидной единой кнопки:

«Сбросить все фильтры»

Поэтому сотрудники используют обходной путь:

* выйти на главную
* снова открыть квартиры

После этого фильтры сбрасываются

В новой системе обязательно нужна заметная функция полного сброса

91. Состояние фильтров

При разработке стоит продумать:

* отображение активных фильтров
* количество активных фильтров
* chips / теги выбранных параметров
* кнопку «Очистить всё»
* сохранённые фильтры
* сохранённые поиски

92. Поиск и сохранённые запросы

Функция заявок фактически уже является очень мощным вариантом сохранённого поиска

В новой системе можно объединить концепции:

* фильтр
* сохранённый поиск
* заявка клиента
* уведомление о новом объекте

Это может существенно упростить архитектуру

93. Мобильная версия - одна из главных проблем

Текущая система практически не адаптирована под телефон

Для доступа с мобильного пользователь делает сложную последовательность действий:

1. открывает Bitrix
2. авторизуется
3. нажимает авторизацию через Bitrix
4. вручную редактирует URL
5. удаляет слово Mobile
6. открывает десктопную версию
7. переворачивает телефон горизонтально
8. открывает нужный раздел
9. снова меняет ориентацию для фильтров

Это крайне неудобно

94. Мобильное приложение

Нативного приложения фактически нет

Ранее существовала мобильная версия, но сейчас она не поддерживается

Работа происходит через браузер

95. Проблемы мобильной работы

На телефоне неудобно:

* искать объект
* открывать фильтры
* работать с карточкой
* добавлять объект
* переключаться между разделами
* редактировать данные

Особенно критично для риелторов, которые много времени проводят вне офиса

96. Добавление объекта с телефона

Есть отдельный серьёзный баг / ограничение

С телефона можно добавить квартиру в ЖК

Но невозможно нормально добавить квартиру просто по улице

Это критичная функциональная дыра

97. Требование к новой системе - mobile first

Новая база обязательно должна быть адаптивной

Минимум:

* полноценная работа с телефона
* создание объекта

* загрузка фотографий
* выбор адреса
* фильтрация
* работа с заявками
* создание подборки
* отправка презентации

Риелтор должен иметь возможность провести практически весь стандартный рабочий процесс со смартфона

98. Общий UX-принцип новой базы

В разговоре несколько раз повторялась мысль:

не нужно переносить старую систему буквально

107. Ключевой сценарий риелтора в новой системе

Идеальный рабочий сценарий можно представить так:

1. риелтор получает нового клиента
2. создаёт клиента
3. создаёт заявку
4. выставляет параметры
5. система сразу показывает подходящие объекты
6. риелтор быстро просматривает их визуально
7. отмечает подходящие
8. формирует web-подборку
9. отправляет клиенту ссылку
10. клиент / риелтор отмечает реакцию
11. неподходящие варианты больше не мешают
12. новые объекты автоматически появляются в заявке
13. система уведомляет риелтора
14. перед показом риелтор проверяет актуальность
15. при необходимости обновляет цену / статус обзвона
16. ответственный объекта получает уведомление
17. дальнейшие действия фиксируются в истории

108. Ключевой сценарий добавления объекта

1. риелтор нажимает «Добавить объект»
2. выбирает тип недвижимости
3. вводит адрес
4. система предлагает существующие адреса
5. если адреса нет - отправляет его на модерацию
6. выбирает / создаёт собственника
7. система проверяет телефон на дубли
8. вводятся характеристики
9. добавляются фотографии
10. фотографии сортируются
11. выбирается, какие фото публичные
12. загружаются документы
13. объект сохраняется как черновик / в продаже
14. офис-менеджер проверяет
15. переводит в «Актуальное предложение»
16. объект становится доступен для сайта и заявок

109. Ключевой сценарий актуализации

1. система определяет объекты, давно не подтверждавшиеся
2. риелтор получает список на актуализацию
3. звонит собственнику
4. фиксирует результат
5. обновляет:
    * цену
    * статус
    * комментарий
6. дата подтверждения актуальности обновляется отдельно от даты редактирования
7. при изменении чужого объекта ответственный получает уведомление

110. Очень важное отличие дат

В новой системе желательно разделить минимум три даты:

* дата создания
* дата последнего редактирования
* дата последнего подтверждения актуальности

Сейчас дата обновления меняется даже от обычного комментария

Из-за этого она не всегда говорит о том, что объект реально проверяли у собственника

111. Общий вывод

Текущая база «Доминанты» - старое технически, но довольно развитое предметно решение

В ней уже сформировалась бизнес-логика реального агентства недвижимости, поэтому при разработке новой системы важно использовать её как источник требований

Но копировать сам интерфейс или структуру Bitrix нет смысла

Новая система должна оставить лучшие механики:

* карточки объектов
* визуальный подбор
* заявки
* автоматический matching
* историю
* статусы
* web-презентации
* роли
* модерацию
* сайт

и при этом решить главные проблемы:

* мобильность
* сложные фильтры
* устаревший UX
* адресный справочник
* дубли
* архитектуру ЖК
* актуализацию
* техническую негибкость

В результате продукт должен ощущаться для риелтора знакомо по логике работы, но значительно быстрее, понятнее и современнее
