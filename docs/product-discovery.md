# База объектов недвижимости — Product Discovery

Статус документа: живой черновик discovery  
Дата последнего обновления: 19 сентября 2026  
Стадия проекта: предварительное обсуждение, до технического задания

## 1. Назначение документа

Документ фиксирует уже подтверждённые требования, текущие продуктовые решения, принятые ограничения и вопросы, которые ещё предстоит согласовать с заказчиком.

Это не финальное техническое задание и не коммерческое предложение. Формулировки из раздела «Открытые вопросы» не считаются утверждённым функционалом.

## 2. Краткое описание продукта

Веб-система для внутреннего ведения базы объектов агентства недвижимости.

Основная задача — позволить сотрудникам агентства совместно создавать, дополнять, актуализировать, искать, отбирать и публиковать объекты недвижимости.

Продукт не позиционируется как классическая CRM. В первой версии не планируются:

- воронка клиентов и сделок;
- канбан;
- полноценная клиентская база;
- биллинг;
- управление несколькими независимыми агентствами через один интерфейс;
- аренда;
- отдельный модуль новостроек и шахматок;
- серый парсинг объявлений с OLX, DIM.RIA и других площадок.

При этом архитектура ядра должна допускать последующее переиспользование разработчиком в отдельном продукте. Исключительные права на программное ядро заказчику не передаются. Данные конкретного агентства принадлежат агентству.

## 3. Масштаб и нагрузка

Реалистичный начальный объём — до 1 000 объектов и около 10 сотрудников.

Упоминавшиеся 55 000 объектов — не прогноз фактического наполнения, а ориентир отсутствия искусственного архитектурного потолка. Для PostgreSQL такой объём карточек не является значительным. Основной рост стоимости при масштабировании создают фотографии, документы, публичный трафик и фоновые интеграции.

## 4. Границы первой версии

### 4.1. Типы недвижимости

В первую версию входят:

- квартиры;
- дома;
- земельные участки;
- коммерческая недвижимость;
- паркинги.

### 4.2. Тип операции

В первой версии поддерживается только продажа.

Не входят:

- долгосрочная аренда;
- посуточная аренда.

В модели данных допускается поле типа операции со значением `sale`, чтобы впоследствии можно было отдельно добавить аренду без перестройки ядра.

### 4.3. География

- Основной и фактически единственный рабочий город первой версии — Одесса.
- Город в карточке по умолчанию заполняется значением «Одесса».
- Поле города не следует жёстко исключать из модели данных, чтобы единичный объект в другом городе не требовал миграции базы.
- Полноценный мультирегиональный справочник и соответствующая продуктовая логика в первую версию не входят.

## 5. Основная модель объекта

В рамках первой версии:

- один физический объект соответствует одной карточке;
- у карточки одно актуальное предложение о продаже;
- не моделируются параллельные предложения разных агентов по одному объекту;
- объект может иметь несколько внешних публикаций: OLX, DIM.RIA, сайт агентства;
- внешние публикации не считаются отдельными предложениями внутри базы.

Предварительная структура:

```text
Объект недвижимости
├── характеристики объекта
├── собственник или партнёр
├── ответственный риелтор
├── цена и история цены
├── актуализации и комментарии
├── фотографии и документы
└── внешние публикации
    ├── OLX
    ├── DIM.RIA
    └── сайт агентства
```

## 6. Минимальная карточка

Для создания минимальной карточки требуются:

- имя контактного лица;
- основной телефон;
- тип недвижимости;
- точный адрес;
- цена;
- валюта;
- ответственный риелтор, назначаемый автоматически;
- количество комнат — только для типов, где оно применимо.

Количество комнат:

- квартира — обязательно;
- дом — обязательно;
- участок — неприменимо;
- паркинг — неприменимо;
- коммерческая недвижимость — правило будет определено отдельно.

Черновик — это уже созданная минимальная карточка, которая может быть не готова к полноценной публикации из-за отсутствующих фотографий, описания или дополнительных характеристик.

Для перевода квартиры из черновика в активный статус дополнительно обязательны:

- административный район;
- общая площадь;
- этаж квартиры;
- общая этажность дома.

Поля площади квартиры:

- общая площадь — обязательна при активации;
- жилая площадь — необязательна;
- площадь кухни — необязательна.

Пользователь может сохранить карточку без этих значений только как черновик. Система должна явно показывать, какие обязательные поля мешают активации.

Итоговый обязательный набор для активной карточки квартиры:

- имя контактного лица;
- основной телефон;
- тип недвижимости «квартира»;
- точный адрес;
- административный район;
- количество комнат;
- общая площадь;
- этаж квартиры;
- общая этажность дома;
- цена;
- валюта;
- ответственный риелтор, назначаемый автоматически.

Другие характеристики улучшают полноту и качество карточки, но не блокируют перевод в активный статус.

### 6.1. Необязательные характеристики квартиры

В карточке квартиры остаются как необязательные структурированные поля:

- жилая площадь;
- площадь кухни;
- тип планировки;
- раздельные или смежные комнаты;
- высота потолков;
- количество санузлов;
- тип санузла;
- балкон;
- лоджия;
- терраса;
- состояние объекта;
- тип ремонта;
- наличие мебели;
- наличие техники.

Полный каталог значений для выпадающих списков будет подготовлен на этапе проектирования. Его не требуется согласовывать по одному значению в рамках первичного онбординга.

### 6.2. Обязательные поля других типов недвижимости

Общие обязательные поля — контакт, телефон, тип недвижимости, адрес, административный район, цена, валюта и ответственный риелтор — применяются ко всем типам объектов.

Дополнительные требования для активации:

| Тип объекта | Дополнительные обязательные поля |
|---|---|
| Дом | Количество комнат, площадь дома |
| Земельный участок | Площадь в сотках, целевое назначение |
| Коммерческая недвижимость | Общая площадь |
| Паркинг | Дополнительных обязательных характеристик нет |

Для дома площадь участка существует в карточке, но не блокирует активацию: сотрудник может не знать её в момент создания объекта.

Для коммерческой недвижимости количество комнат и подтип объекта пока не являются обязательными. Подтипы будут проработаны позднее с учётом практики агентства.

Для паркинга достаточно общих обязательных полей, включая адрес и цену. Подтип, площадь, уровень и другие характеристики остаются необязательными.

### 6.3. Дополнительные поля других типов

Дом:

- площадь участка;
- этажность;
- количество спален;
- жилая площадь и площадь кухни;
- материал дома и год постройки;
- состояние и ремонт;
- отопление, вода, газ, канализация и электричество;
- гараж, подвал, хозяйственные постройки и бассейн.

Земельный участок:

- кадастровый номер;
- наличие сервитутов и других ограничений;
- форма участка;
- ширина фасада;
- рельеф;
- подъездная дорога;
- вода, газ, канализация и электричество;
- существующие строения.

Коммерческая недвижимость:

- подтип или предполагаемое назначение;
- этаж и этажность;
- отдельный вход;
- фасадность и витрины;
- высота потолков;
- мощность электричества;
- отопление, вода и канализация;
- состояние и ремонт;
- парковка;
- наличие действующего арендатора.

Паркинг:

- подтип: парковочное место, место в подземном паркинге, гараж, гаражный бокс или другое;
- площадь и размеры;
- уровень или этаж;
- номер места;
- крытый или открытый;
- подземный или наземный;
- охрана и видеонаблюдение;
- электричество.

Все поля этого подраздела необязательны для активации.

## 7. Жизненный цикл объекта

### 7.1. Основные статусы

- `draft` — черновик;
- `active` — активный объект;
- `reserved` — объект под резервом;
- `archived` — архив.

«Продан» и «Снят с продажи» являются причинами архивирования, а не самостоятельными постоянными статусами.

Предварительные причины архивирования:

- продан;
- собственник снял с продажи;
- дубль;
- ошибочно добавлен;
- другая причина.

Любой риелтор может отметить объект проданным или снятым с продажи. Действие обязательно записывается в журнал.

### 7.2. Полнота карточки

Полнота данных не смешивается с основным статусом объекта.

Система отдельно может показывать предупреждения:

- отсутствуют фотографии;
- отсутствует описание;
- отсутствуют обязательные характеристики;
- есть ошибки, мешающие публикации на конкретной площадке.

Активный объект может оставаться активным и одновременно требовать дополнения данных.

### 7.3. Актуальность

Состояние актуальности хранится отдельно:

- подтверждено;
- скоро требуется подтверждение;
- подтверждение просрочено.

Предварительные интервалы проверки:

- каждые 7 дней;
- каждые 14 дней.

Можно установить значение по умолчанию для агентства и выбранный интервал для отдельного объекта.

Просрочка создаёт внутреннее напоминание, но не выполняет автоматических разрушительных действий:

- объект не скрывается автоматически;
- не удаляется из подборок;
- не снимается с публикаций;
- не архивируется.

Решение принимает сотрудник.

При подтверждении актуальности сохраняются:

- дата и время;
- сотрудник, выполнивший проверку;
- результат связи;
- необязательный комментарий;
- следующая дата проверки.

## 8. Командная работа и права

### 8.1. Общий принцип

База работает как единый организм. Закрепление объекта определяет ответственность и публичный контакт, но не запрещает коллегам поддерживать сведения в актуальном состоянии.

Вся база и контакты собственников видны всем риелторам агентства.

### 8.2. Ответственный риелтор

У каждого объекта есть:

- `created_by` — кто создал карточку;
- `responsible_agent` — кто ведёт объект сейчас.

Телефон ответственного риелтора должен использоваться во внешних объявлениях и публичных материалах, если не будет согласовано другое правило.

Сменить ответственного могут руководитель или администратор. Переназначение сохраняется в журнале.

### 8.3. Действия обычного риелтора

Любой риелтор может, в том числе для чужого объекта:

- подтвердить актуальность;
- изменить цену после разговора с собственником;
- дополнить описание и характеристики;
- добавить фотографии;
- добавить новый номер телефона;
- оставить комментарий;
- поставить объект в резерв;
- отметить объект проданным;
- отметить объект снятым с продажи;
- отправить объект в архив с указанием причины.

Это предотвращает ситуацию, при которой важная информация теряется, пока ответственный сотрудник недоступен.

### 8.4. Защищённые действия

Предварительно ограничиваются:

- смена ответственного — руководитель или администратор;
- окончательное удаление без возможности восстановления — администратор;
- бесследное изменение или удаление основного телефона собственника — запрещено;
- очистка журнала действий — недоступна обычному пользователю.

Риелтор может добавить новый телефон или отметить прежний как неактуальный. Старое значение и автор изменения сохраняются в истории.

### 8.5. Предварительные роли

- риелтор;
- руководитель;
- администратор системы.

Окончательная матрица прав будет составлена в техническом задании.

## 9. Контакты

Для прямого объекта хранятся:

- имя собственника или контактного лица;
- основной телефон;
- дополнительные телефоны;
- Telegram;
- Viber;
- WhatsApp;
- текущая важная заметка;
- история актуализаций и коммуникаций.

Текущая заметка может содержать, например:

- предпочтительное время звонка;
- допустимое время показов;
- временную недоступность;
- другие важные условия.

История действий не должна затираться при обновлении текущей заметки.

## 10. Прямые и партнёрские объекты

Вместо бизнес-поля «источник лида» используется тип связи с объектом:

- прямой объект — агентство имеет контакт собственника;
- партнёрский объект — контакта собственника у агентства нет, взаимодействие идёт через партнёра.

Для партнёрского объекта:

- явно сохраняется признак партнёрского объекта;
- контакт собственника отсутствует;
- может храниться информация о партнёре;
- назначается внутренний ответственный риелтор;
- в публичных материалах используется контакт агентства или ответственного риелтора.

Отдельное поле «откуда узнали об объекте: OLX, звонок, сайт» пока считается избыточным и в первую версию не входит.

Способ создания записи — вручную, импортом, из файла или письма — может сохраняться технически в журнале, но не требует ручного заполнения сотрудником.

## 11. Эксклюзивность

Эксклюзив не является отдельным договорным модулем. Это специальный признак приоритетного объекта.

Для первой версии обязательны:

- обычный объект;
- эксклюзивный объект;
- дата начала эксклюзива.

Эксклюзивные объекты должны быть заметно выделены в интерфейсе и доступны через отдельный фильтр или представление приоритетных объектов.

Эксклюзивные объекты потенциально содержат больше подтверждённых сведений и чаще могут включать загруженные документы.

В первую версию не входят как отдельные структурированные поля:

- дата окончания эксклюзивного договора;
- номер договора;
- процент комиссии;
- расширенный договорный процесс.

При необходимости комиссия и другие детали временно могут храниться во внутреннем комментарии. Полноценный модуль эксклюзивных договоров может быть уточнён или добавлен позднее.

## 12. Цена и валюта

### 12.1. Основная цена

- В карточке хранится цена собственника.
- Комиссия агентства и итоговая цена для клиента пока не входят в подтверждённый объём.
- История изменения цены обязательна.
- Каждое изменение сохраняет старое значение, новое значение, автора и время.

### 12.2. Валюты

Поддерживаются:

- USD;
- UAH.

Сохраняются исходная цена и исходная валюта. Результат конвертации не перезаписывает исходное значение.

### 12.3. Курс

Для первой версии выбран официальный курс НБУ с обновлением один раз в сутки, ориентировочно в 10:00.

У НБУ нет отдельных курсов покупки и продажи — публикуется один официальный курс на дату. Поэтому гривневый эквивалент по НБУ является справочным отображением, а не гарантированной суммой сделки.

Если агентство захочет использовать нижний наличный курс покупки, потребуется отдельное решение:

- выбрать конкретный коммерческий источник;
- либо позволить руководителю задавать внутренний курс на день.

В интерфейсе источник курса должен быть явно обозначен.

## 13. Адрес и публичность

Внутри системы хранится полный адрес, включая номер квартиры и точные координаты, если они указаны.

### 13.1. Глубина локации

Для Одессы требуется подробный структурированный справочник локаций, а не только четыре административных района и свободное текстовое поле.

Предварительная иерархия:

```text
Город
→ административный район
→ рыночная зона / микрорайон
→ уточняющая подзона или станция
→ улица
→ дом / корпус
→ квартира
```

Справочник должен учитывать привычную для одесского рынка лексику и позволять точно фильтровать объекты. Среди примеров:

- Таирова;
- Черёмушки;
- Аркадия;
- Молдаванка;
- Слободка;
- Ближние Мельницы;
- Дальние Мельницы;
- Ленпосёлок;
- посёлок Котовского;
- Лузановка;
- станции Большого Фонтана, включая деление от 1-й до 16-й станции.

Административный район, рыночная зона и уточняющая подзона не должны смешиваться в одном поле. Например, «Приморский район», «Аркадия» и «5-я станция Большого Фонтана» являются разными уровнями описания.

Для активации объекта обязательны:

- точный адрес;
- административный район.

Рыночная зона / микрорайон и уточняющая подзона необязательны. Сотрудники заполняют их при наличии информации, но отсутствие этих значений не должно блокировать активацию объекта. Это позволяет сохранить подробную фильтрацию там, где данные заполнены, не создавая чрезмерного барьера для сотрудников.

Полный перечень, границы и синонимы локаций необходимо подготовить отдельно и проверить с агентством. Случайные ориентиры вроде «район парка Горького» могут оставаться в описании или комментарии и не обязаны становиться системной локацией.

Во внешних подборках и публикациях никогда не показываются:

- номер квартиры;
- телефоны и мессенджеры собственника;
- внутренние комментарии;
- история звонков и изменений;
- внутренние документы.

Предварительно для публичного адреса могут использоваться уровни:

- улица и дом;
- только улица;
- только район.

Приблизительная точка на карте в первую версию пока не подтверждена.

## 14. Характеристики домов и жилых комплексов

Отдельный справочник домов и жилых комплексов в первую версию не входит.

Поля заполняются непосредственно в карточке объекта:

- название ЖК — свободный текст;
- тип дома;
- материал стен;
- год постройки;
- этажность;
- другие характеристики.

Тип дома, материал стен и год постройки являются необязательными. Отсутствие значений вроде «чешка», «хрущёвка», «сталинка», материала стен или года постройки не мешает активировать объект.

Не реализуются:

- наследование характеристик от общей карточки дома;
- унификация названий ЖК;
- автозаполнение из каталога новостроек;
- шахматки застройщика как самостоятельный модуль.

В будущем каталог ЖК, домов, корпусов и шахматок может быть предложен как отдельный платный модуль.

Важно различать:

- тип объекта: квартира, дом, участок, коммерция, паркинг;
- тип/возраст дома: новый дом, хрущёвка, сталинка и т. п.

Разделение рынка на первичный и вторичный в текущую версию не входит. Система предназначена для вторичной базы. Первичный рынок и работа с квартирами от застройщика считаются отдельным будущим модулем.

При этом квартира вторичного рынка может находиться в новом доме. Значения вроде «новый дом», «хрущёвка», «сталинка» относятся к характеристикам здания, а не к типу рынка.

## 15. Документы

Для обычного объекта информация о документах в большинстве случаев фиксируется со слов собственника без требования загрузить файлы.

Предварительно хранятся:

- вид правоустанавливающего документа;
- год или дата документа;
- проверен ли документ;
- кто и когда проверил;
- внутренний комментарий;
- отметка «информация со слов собственника».

Загрузка файлов:

- необязательна;
- наиболее актуальна для эксклюзивных объектов и объектов, приближающихся к сделке;
- может включать правоустанавливающие документы, техпаспорт и другие материалы;
- окончательный перечень документов не согласован.

Фотографии объекта и приватные документы должны храниться раздельно. Для документов предполагаются:

- закрытое объектное хранилище;
- отсутствие постоянных публичных ссылок;
- временный авторизованный доступ;
- журнал просмотров и скачиваний;
- отдельный режим для паспортных и иных чувствительных документов.

Внутри агентства все авторизованные риелторы могут:

- просматривать загруженные документы;
- загружать документы в любой объект, включая объект другого ответственного риелтора.

Все загрузки и действия с документами фиксируются в журнале. Наружу, в публичные подборки и объявления, документы не передаются.

После продажи или архивирования документы пока сохраняются бессрочно вместе с объектом. Возможный срок хранения и автоматическое удаление считаются будущей операционной политикой и не входят в обязательную логику первой версии.

## 16. Фотографии

Объект может содержать набор фотографий. Подтверждена возможность добавления фотографий и предупреждение при их отсутствии.

Предварительный технический подход:

- проверка формата и размера при загрузке;
- нормализация ориентации;
- удаление лишних метаданных;
- создание веб-версии;
- создание миниатюры;
- опциональная версия с водяным знаком;
- хранение в S3-совместимом объектном хранилище, например Cloudflare R2.

Правила порядка фотографий, лимиты, оригиналы и водяные знаки ещё не согласованы.

## 17. Поиск, подборки и отправка клиенту

Система должна позволять искать и фильтровать объекты, формировать подборки и отправлять клиенту публичную ссылку.

### 17.1. Основное представление базы

База должна поддерживать два равноправных режима отображения:

- карточки с фотографиями — для визуального просмотра по аналогии с агрегаторами недвижимости;
- плотный список / таблица — для быстрого рабочего просмотра и последовательного поиска большого количества объектов.

Пользователь может переключаться между режимами, не теряя текущий поиск, фильтры и сортировку. Желательно запоминать последний выбранный режим пользователя.

### 17.2. Массовые действия

Пользователь может выбрать несколько объектов и выполнить массовое действие, включая:

- назначить или сменить ответственного риелтора;
- архивировать;
- подтвердить актуальность;
- отправить на публикацию.

Массовые действия должны требовать подтверждения, показывать количество выбранных объектов и записываться в журнал по каждому затронутому объекту. Ошибка по одному объекту не должна скрывать результат обработки остальных.

### 17.3. Мобильная работа

Добавление и редактирование объекта должны быть полноценно удобны со смартфона:

- адаптивная короткая форма создания;
- доступ к полной карточке;
- загрузка фотографий из галереи или файлов телефона;
- выполнение основных оперативных действий.

Отдельная камера внутри приложения и собственный интерфейс фотосъёмки не разрабатываются. Мобильный браузер может предложить системную камеру как стандартный источник файла, но это не является отдельным модулем продукта.

Подборка рассматривается как отдельная сущность и потенциально содержит:

- название;
- автора;
- выбранные объекты;
- публичный токен ссылки;
- срок действия;
- скрываемые поля;
- события открытия;
- просмотренные клиентом объекты.

Основной формат отправки — ссылка. PDF не является приоритетом; его можно добавить позднее как дополнительную функцию или печатное представление.

Для Telegram возможны разные уровни:

1. Кнопка «Поделиться в Telegram», открывающая выбор чата у риелтора. Бот не нужен.
2. Автоматическая отправка через бота, если клиент ранее начал взаимодействие с ботом.
3. Отдельная интеграция с Telegram Business.

Для компактной первой версии предпочтителен первый вариант. Полноценный Telegram-модуль пока не подтверждён.

## 18. Импорт и наполнение

Подтверждённые способы наполнения:

- ручное создание;
- постоянный пользовательский импорт Excel/CSV;
- официально полученные файлы партнёров;
- в перспективе — обработка прайсов и шахматок застройщиков из почты, файлов или ссылок.

Excel/CSV является функцией продукта, а не только разовой услугой разработчика. Сотрудник должен иметь возможность в дальнейшем самостоятельно загрузить новую таблицу, например пакет из 24 объектов от инвесторов.

Предварительный пользовательский процесс импорта:

```text
Загрузка файла
→ выбор листа при необходимости
→ сопоставление колонок с полями системы
→ предварительная проверка
→ предупреждения об ошибках и вероятных дублях
→ подтверждение импорта
→ отчёт: создано / обновлено / пропущено / ошибка
```

Первичный перенос существующей базы заказчика может быть выполнен разработчиком отдельно, но не заменяет постоянный инструмент импорта.

Не планируется серый массовый парсинг публичных объявлений OLX, DIM.RIA и других площадок.

Импорт шахматок рассматривается как отдельный будущий конвейер:

```text
Файл поставщика
→ распознавание структуры
→ приведение к внутреннему формату
→ поиск существующих записей
→ создание/обновление/снятие
→ отчёт об ошибках и расхождениях
```

Разные поставщики могут потребовать отдельных адаптеров. Полноценный модуль новостроек не входит в первую версию.

## 19. Дубли

Контроль дублей обязателен, но точные правила ещё не утверждены.

Потенциальные признаки совпадения:

- полный адрес и номер квартиры;
- телефон собственника;
- площадь, этаж и количество комнат;
- похожие фотографии;
- похожий текст;
- внешний идентификатор импорта.

Система не должна автоматически необратимо объединять записи без понятного правила или подтверждения пользователя.

## 20. Внешние публикации

Необходимы:

- будущая публикация на сайт агентства;
- интеграция с OLX;
- интеграция с DIM.RIA;
- отображение статуса публикации и ошибок.

Интеграции с OLX и DIM.RIA входят в общий согласованный объём первой поставки и не продаются заказчику как отдельное дополнение. Реализация поставки может быть поэтапной:

1. сначала запускается рабочее ядро базы;
2. затем в рамках той же поставки подключаются внешние публикации.

Для первой версии используется по одному корпоративному аккаунту агентства на каждой площадке:

- один корпоративный аккаунт OLX;
- один корпоративный аккаунт DIM.RIA.

Выбор отдельного портального аккаунта конкретного риелтора при публикации не требуется. При этом внутри объявления желательно использовать контакт ответственного риелтора, если правила и возможности площадки это допускают.

Предварительная архитектура использует внутренний единый формат и отдельные адаптеры площадок.

```text
Карточка объекта
→ проверка данных
→ внутренний формат публикации
→ адаптер OLX / адаптер DIM.RIA / API сайта
```

OLX предоставляет Partner API с OAuth 2.0. Приложение требует регистрации и одобрения, а действия выполняются в контексте авторизованного аккаунта.

DIM.RIA поддерживает XML-импорт для соответствующих корпоративных пакетов. Фид периодически забирается площадкой. Конкретные условия подключения должны быть подтверждены заказчиком через менеджера DIM.RIA.

## 21. Журнал действий и удаление

Аудит должен работать с первой версии, даже если матрица ролей будет уточняться позднее.

Фиксируются:

- создание объекта;
- изменение характеристик;
- изменение цены;
- добавление и изменение контактов;
- актуализация;
- смена ответственного;
- изменение статуса;
- архивирование и восстановление;
- действия с документами;
- публикации и ошибки интеграций.

Основное удаление — мягкое: объект архивируется или помещается в корзину. Физическое удаление — отдельное административное действие.

## 22. Предварительная техническая архитектура

Рабочий вариант:

- интерфейс: React / Next.js;
- backend: TypeScript / NestJS либо совместимое существующее ядро разработчика;
- база данных: PostgreSQL;
- гибкие дополнительные характеристики: JSONB только там, где это оправдано различиями типов недвижимости;
- фотографии и файлы: Cloudflare R2 или другое S3-совместимое хранилище;
- фоновые задачи: сначала внутри backend и через cron; отдельная очередь добавляется при реальной необходимости;
- поиск: PostgreSQL на первой стадии;
- размещение: Railway;
- журналирование и резервные копии: встроенные возможности Railway плюс периодический `pg_dump` в объектное хранилище.

Несмотря на разработку для одного агентства, в основных таблицах целесообразно предусмотреть `organization_id`, чтобы ядро можно было позднее превратить в продукт. Биллинг, переключение организаций и SaaS-интерфейс в текущую версию не входят.

## 23. Предварительная стоимость инфраструктуры

Для фактического сценария — около 1 000 объектов и 10 сотрудников — ожидается:

- минимальная рабочая конфигурация: примерно $5–10 в месяц;
- нормальная отдельная конфигурация: примерно $10–25 в месяц;
- отдельный Railway Pro workspace: ориентировочно от $20 в месяц с учётом включённого usage;
- рост до $30–60 возможен при увеличении трафика, фоновых процессов и объёма файлов.

Диапазон $150–400 в месяц не относится к текущему проекту и был признан завышенным для данного сценария.

Пример фотографий:

```text
1 000 объектов × 15 фотографий × 1,5 МБ = 22,5 ГБ
```

При тарифе R2 $0,015 за ГБ и бесплатных первых 10 ГБ хранение такого объёма составляет ориентировочно $0,19 в месяц без учёта операций.

В коммерческом предложении следует разделять:

1. разработку;
2. фактическую инфраструктуру;
3. техническое сопровождение;
4. новые функции и интеграции.

## 25. Открытые вопросы

### Карточки разных типов

- Обязательный набор для активной карточки квартиры утверждён в разделе 6; дополнительные поля не должны расширять его без отдельного решения.
- Базовые обязательные и дополнительные поля всех пяти типов утверждены в разделе 6.
- Точные значения справочников и дополнительные отраслевые характеристики уточняются на этапе проектирования и ревью.
- Подтипы коммерческой недвижимости требуют дополнительной проверки с агентством из-за ограниченного текущего опыта работы с этим сегментом.

### Фотографии

- Максимальное количество и размер.
- Хранить ли исходные оригиналы?
- Правила сортировки и главное фото.
- Водяной знак: когда и какой.

### Адрес и карта

- Подготовить и согласовать полный иерархический справочник локаций Одессы, включая синонимы.
- Административный район и точный адрес обязательны; микрорайон и подзона необязательны.
- Нужна ли карта в первой версии?
- Какой уровень адреса показывать по умолчанию в публичной подборке?
- Нужна ли намеренно смещённая точка?

### Публикации

- Подтверждено: по одному корпоративному аккаунту агентства для OLX и DIM.RIA.
- Подтверждено: обе интеграции входят в первую поставку, но подключаются после запуска ядра базы.
- Какие категории и обязательные поля потребуются для каждого типа объекта?
- Как обрабатывать модерацию, отклонения и платные лимиты?
- Какой корпоративный пакет DIM.RIA использует агентство?

### Подборки

- Срок жизни публичной ссылки.
- Нужна ли защита паролем?
- Какие события просмотра необходимо фиксировать?
- Нужно ли клиенту отмечать понравившиеся объекты?

### Импорт и дубли

- Формат существующей базы заказчика.
- Объём и качество исходных данных.
- Правила объединения дублей.
- Постоянный пользовательский импорт Excel/CSV подтверждён.
- Детально спроектировать сопоставление колонок, предварительную проверку и отчёт об импорте.

## 26. Завершение discovery и переход к проектированию

Первичный онбординг не должен превращаться в согласование каждого поля и значения справочника. Стандартные технические и объектные характеристики проектируются разработчиком и затем показываются заказчику на ревью.

Три завершающих смысловых блока согласованы:

1. определены отличия карточек дома, участка, коммерческой недвижимости и паркинга от карточки квартиры;
2. определён основной пользовательский путь: список объектов → создание/редактирование → поиск → подборка → публикация;
3. зафиксированы границы интеграций и постоянного импорта для первой версии.

Первичный discovery завершён 19 сентября 2026 года. Оставшиеся вопросы в разделе 25 не блокируют проектирование и должны решаться в техническом дизайне либо вместе с заказчиком до реализации соответствующего модуля.

После этого discovery считается завершённым и начинается проектирование:

- карта экранов и пользовательских сценариев;
- логическая модель данных и связи сущностей;
